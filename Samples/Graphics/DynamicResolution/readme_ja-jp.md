#   Dynamic Resolution サンプル

*\* このサンプルは Microsoft Game Development Kit (2020 年 6 月)
と互換性があります。現在、Xbox One X コンソール
モードはサポートしていません。*

# 

# 説明

このサンプルでは、パフォーマンス条件の変化に対応して解像度を調整することで、フレーム
レートを維持する方法について説明します。

# ![](./media/image3.jpeg)

# サンプルのビルド

Project Scarlett を使用する場合は、アクティブ ソリューション
プラットフォームを Gaming.Xbox.Scarlett.x64 に設定します。

Xbox One 開発キットを使用している場合は、アクティブ ソリューション
プラットフォームを Gaming.Xbox.XboxOne.x64 に設定します。

*詳細については、GDK
のドキュメントの*「サンプルの実行」*を参照してください。*

# サンプルの使用方法

このサンプルは、次のコントロールを使用します。

| 操作                                   |  ゲームパッド                |
|----------------------------------------|-----------------------------|
| 画面上のメニュー内を移動する           |  左サムスティック/D パッド   |
| 動的な解像度のオン/オフを切り替える    |  Y ボタン                    |
| カメラを一時停止する                   |  X ボタン                    |
| サイドパネルを非表示または表示する     |  A ボタン                    |
| サンプルを終了する                     |  ビュー ボタン               |

# 実装上の注意

## アルゴリズム

このサンプルの目的は、以下の 3 つの判断を下すことです。

1.  現在の解像度で、近い将来にタイトルを使用してフレームをドロップしますか。

2.  解像度を下げることは、フレームのドロップの回避に役立ちますか
    (すなわち、パフォーマンスは GPU 負荷によって制約を受けますか)。

3.  タイトルは、さらなる高解像度でフレーム レートを維持できますか。

この目的をテストするために、サンプルでは、ゲームのさまざまな種類のフレーム
レートの不安定性をモデル化することを目的とした、多くの仮想的シナリオが生成されます。

1.  GPU 負荷の一時的なスパイク

2.  GPU 負荷の持続的なオーバーラン

3.  CPU 負荷の持続的なオーバーラン

これらのシナリオの望ましい結果には (それぞれ) 次のものがあります。

1.  解像度を下げ、スパイクの通過後に解像度を上げます

2.  フレーム レートを維持するために必要な最低限の量だけ解像度を下げます

3.  何もしません (解像度は CPU 負荷には影響しません)

このサンプルのコア アルゴリズムは **Sample::DetermineResolution**
関数に存在します。サンプルの他のコードの多くは、フレーム
レートのシミュレーションおよび入念な測定とグラフ化に特化しています。ゲーム
エンジンで動的解像度を実装している場合は、後者のコードをポートする必要はありません。

サンプルは、カメラが動くまで解像度の変更を待機します。解像度の変化は静的なシーンでは目立ちますが、動くシーンでは通常気付きません。このため、静的な要素
(UI など)
は固定の解像度に保つことをお勧めします。このサンプルでは、メイン
シーンを背景の表示面にレンダリングし、UI
要素を前景の表示面にレンダリングすることで、この目標を達成します。背景面は、プロセッサの負荷に応じた解像度の動的な変更がサポートされています。前景面は、1920
x 1080 の固定解像度でレンダリングされています。

可能であれば、タイトルでは、固定の垂直解像度を維持し、水平解像度のみを下げることを推奨します。この推奨理由には次の
2 つの要素があります。

1.  ハードウェア スケーラーでは、y 方向よりも x
    方向で多くのタップを必要とするため、水平方向のアップスケールの方が上手く作業できます。

2.  ほとんどのゲーム モーション (カメラやオブジェクトによる) では x
    方向を好む傾向があるので、水平解像度の変化の方が目立ちにくくなります。

## エイリアス レンダリング ターゲット

メモリ使用量を増やさずに任意の数の解像度を有効化するために、サンプルでは、すべてのシーン
レンダー ターゲットおよび
深度ターゲットがそれぞれ同じメモリにエイリアス化されます。たとえば、サンプルが起動すると、1920
x 1080 レンダー ターゲットが作成されます。解像度を 1728x1080
に変更すると、元のレンダー ターゲットと同じメモリ割り当てで新たに
*配置されたリソース*
が作成されます。これは、解像度が再び変更されるまで、新しい小規模のレンダー
ターゲットとして使用されます。同時にアクティブな解像度は 1
つに限られるため、1920x1080 レンダー ターゲットおよび 1728x1080 レンダー
ターゲットは、競合せずにメモリを共有できます。深度ターゲットも同じように動作します。

**ResolutionData**
構造体は、特定の解像度でレンダリングするために必要なリソース
(記述子ハンドルおよび D3D リソース) を保持します。**ResolutionSet**
クラスは、ResolutionData
構造体のセットを管理し、解像度が変更されたときに必要に応じて新しい配置されたリソースを作成することに関与します。サンプルでは
1 つの ResolutionSet
のみを使用してシーンをレンダリングしますが、ゲームで複数のレンダー
ターゲット (例として遅延レンダラーなど)
がある場合、複数を使用する場合があります。

このサンプルでは、現在のレンダー ターゲットから固定サイズスワップ
チェーンの左上隅にテクスチャのコピーが実行されることに注意してください。これは、サンプルがすべてを
1
回のパスでレンダリングするのに十分に単純であるという理由でしかありません。実際のゲームでは、最終的な全画面表示のパスはスワップ
チェーンの左上に直接レンダリングできます。どちらの場合も、ID3D12CommandQueue::P
resentX を呼び出し、表示させるスワップ
チェーンのどちらかの部分を示す場合に、D3D12XBOX_PRESENT_PLANE_PARAMETERS::p
SrcViewRects が使用されます。

## 分析の結果

このサンプルでは、パフォーマンスを瞬時、また時間をかけて分析するのに役立ついくつかのグラフとインジケーターを描画します。

**グラフ:**

-   ピクセル計算 (%) -- 理想的な解像度である 1920x1080
    に対する合計ピクセル数の割合。

-   フレーム時間 (ミリ秒) -- スワップ
    チェーンの連続した"フリップ"間の時間。個々のドロップ済みフレームは、このグラフのスパイクとして表示されます。

-   垂直同期マージン (ミリ秒) --
    フレームが準備できた時点と、それを表示するようにスケジュールされた時点の間の時間。個々のドロップ済みフレームで、このグラフを
    0 ミリ秒の基準値の下にドロップさせます。

**インジケーター:**

-   平均 FPS -- スライディングウィンドウ全体の平均フレーム レート。

-   テア -- テアリングが発生した画面上の垂直点 (2
    つのフレームによる時間差)。画面の上部はテアリングがないことを表します。

確認済みのパフォーマンスに対する動的な解像度による方法がどのように影響するか理解するには、2
つのインジケーターを数秒にわたって監視してから、B
ボタンを使用してこの方法のオン/オフを切り替えます。回転シーンに焦点を合わせ、テアおよびドロップ済みフレームを直接抽出しようとすることも可能です。

# 既知の問題

このサンプルでは、June 2020 GDK
およびリカバリ、またはそれ以降のバージョンが必要です。

Gaming.Xbox.XboxOne.x64
構成をビルドする場合、このサンプルは複数の表示面を使用するため、Xbox One
X のコンソール モードでは実行されません。コンソール モードの設定を Xbox
One または Xbox One S に変更することで、Xbox One X
の開発キットで実行できます。また、Project Scarlett の開発キットで
Gaming.Xbox.Scarlett.x64 構成を実行することもできます。

デバッグ ビルド構成のサンプルを実行する場合、追加の CPU
オーバーヘッドによって動的解像度の効果が低下する可能性があります (特に
Xbox One のコンソール
モードの場合)。最適な結果を得るには、プロファイル構成またはリリース構成で実行します。

動的な解像度による方法には、各タイトルの入念なチューニングが必要となります。タイトルのパフォーマンスのプロフィール
(一般的な状況と極端な状況の両方が含まれます)
によっては、さまざまな定数の値を調整する必要が生じる場合があります。

このサンプルでは、異常終了時、コンソールが一時的にハングアップしたように見える場合があります。この動作は、実験の目的で特定のプロセッサの負荷を実行するために使用される"待機"メカニズムによるものです。動的な解像度による方法によって、ゲームでこのような動作が生じることはありません。
