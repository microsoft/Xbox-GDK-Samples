# 説明

このサンプルには、これまでの VRS サンプルと比べて、さらに最適化された
VRS シェーディング レート画像のシェーダーが含まれています。

このサンプルには、スパース
遅延ライティングが実装されてます。それを使用して、VRS で
G-バッファーがレンダリングされます。次に、同じ三角形で同じ
G-バッファー値を持った、ライティングの隣接ピクセルの冗長性を回避する、明るさのピクセルのバッファーを構築します。このピクセルのサブセットを点灯させ、値を水平、垂直、または対角方向にコピーします。このサンプルで、VRS
およびスパース ライティングの両方から GPU
を大幅に削減する方法について説明します。

このサンプルでは、圧縮された深度における平面の方程式を使用するか、SV_Coverage
および SV_ShadingRate
を使用して、ライティングするピクセルのサブセットを計算する 2
つの異なる方法を提供します。この後者の方法では、4 ビットの
G-バッファー領域が必要であり、"拡張された"深度のタイル、または PC
で必要となります。

このサンプルで、レイ マーチングのソフト
シャドウが大きなコストとなっている、遅延ライティングパスに必要なウェーブの総数を削減する方法について説明します。スパース
SSR、SSAO、SSGI、スクリーン スペース シャドウ
マスク、フォグなど、同じ手法やバッファーを使用することで、他のスパース
パスが有効になります。このサンプルには、フレームごとに点灯するピクセルの"回転"が実装されてます。これは、TAA
と組み合わせると役立ち、地上検証データを収束します。

最後に、このサンプルで、次の処理として "VRS
のブロック"を削除する方法である"デブロッキング"について説明します。

# 実装上の注意

画面は 16 x 16 のタイルに分割され、それぞれがカウント
(一つのテクスチャに R8 エントリ) およびタイルあたり最大 224 DWORD
のペイロード データを持っています。ペイロードの DWORD は、それぞれ 4
つのビットの x/y 座標と関係するタイル、21 ビットの unorm
形式の深度、およびライティング計算の最終結果を水平、垂直、または対角方向にコピーするかどうかを示す
3 つのビットで構成されています。タイルのライティング計算の数が 224
を超える場合、Wave32 では早期に出力されないため、従来どおりに 256
ピクセルすべてが点灯します。

すべてのピクセルをライティングするのに十分な Wave
がディスパッチされ、ピクセル数が減少することによって、Wave
がタイル上で早期に出力されると、成功となります。同じ 16 x 16
タイル内のピクセルを処理する作業を伴う各ウェーブ、つまり、ライト
リストは依然としてウェーブのスカラー、すなわち重要となる最適化の状態のままです。

シェーダーの開始時に SparseLightingPrefix84
を呼び出し、シェーダーの終了時に SparseLightingPostfix
を呼び出すことで、スパース
ライティングをサポートするように遅延ライティング
シェーダーを変更するのは簡単なことです。

最も対象となる可能性があるシェーダーには、次のものが含まれます。

1.  GenerateShadingRateCS.hlsl

2.  DepthjDecompressAndBuildSparseBuffersCS.hlsl

3.  SparseLightingCommon.hlsli

4.  LightingShader.hlsli

5.  Deblock.hlsli

6.  SparseLightingShowPixelCopiesCS.hlsl もまた、デバッグ
    シェーダーとして学習する対象となる可能性があります。

また、このサンプルには、圧縮された reverseZ を受け取り、前方に線状の Z
を出力する深度解凍コンピューター シェーダーも実装されています
(DepthDecompress.hlsl を参照)

# 既知の問題

シェーディング
レートの決定は一時的に不安定な場合もあり、次のデブロッキング処理によってこれを悪化させて、VRS
のブロックが削除される可能性があります。通常、TAA
はこのわずかな不安定性を隠して、地上検証データを収束しますが、このサンプルには
TAA が実装されていません。
