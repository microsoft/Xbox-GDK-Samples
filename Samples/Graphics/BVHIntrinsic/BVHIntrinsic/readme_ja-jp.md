# 実装メモ

## 三角形/ドラゴン シーン

LOD 7 による表示の BVH は、Intel Lobree の BVH ビルダー C++ API を使用して構築されました。 ビルド後、BVH をハードウェアに依存しない FP16 AABB と
三角形から変換するパスが実行されました。 バッファーの末尾に追加されているのは、モデル内にある三角形の数を示す単一の DWORD です。 ファイル内の最初の 64 バイトは、このBVH の 'ルート ノード' を表します。 シェーダー "RaytraceTriangles.hlsl" は、ルート ノードから最終的な三角形のヒットまたはミスへの BVH の走査を担当します。 このコンピュート シェーダーは、後から追加される可能性のあるノードをツリーに格納できるよう、スレッドあたり 28 DWORD の小さなスタックを維持します。 '28' という数値は、デモで使用されているコンテンツを確認することによって実験的に導き出されたものです。 LDS 使用率は高い占有率の制限要因であるため、スタック サイズをできるだけ小さくしておくことで、CU/WGP で実行されるウェーブの数を最大化します。

コア トラバーサル ループは見かけによらずシンプルで、次の手順を実行します:

1) トラバーサル ループ内の次のノード (最初はルート ノード) に対してレイを交差させます

2) このノードが三角形ノードの場合:

a.   ヒットまでの 't' 距離を計算します (外れた場合、't' は無限大です)。

b.   このヒットが以前の最も近いヒットよりも近かったかどうかを判断します。

i.  その場合は、ヒット距離、最も近いノード ポインター、三角形 ID を更新します

ii. そうでない場合は、何もしません

c.   手順 4 でスタックから 1 つポップするように次のノード ポインターを InvalidNodePtr に設定します。

3) このノードが FP16 AABB ノードの場合:

a.   有効かどうかに関係なく、追従する次のノードとして最も近い AABB ヒット (childPtrs.x) を設定します。

b.   他の 3 つの AABB については、有効な場合は距離の逆順でスタックにプッシュします。

4) ループの次の反復において追従する別のノードがない場合...

a.   使用可能な場合にはスタックから 1 つポップします

5) それでも次にたどるべき別のノードがまだない場合、その時点でトラバーサルが終了します。

返された RaytraceResults 構造体には、ヒットに関する情報が含まれています:

- 'hit' -- 三角形にヒットしたかどうか。

- 'leafIndex' -- そのヒットがどの三角形**ノード**からのものであるかを一意に識別するインデックス

- "nearestT" -- 最も近いヒットまでのヒット距離、または、ヒットがない場合は無限大。

- 'numIterations' -- 光線が完了するまでにかかった BVH の上下のステップ数

- 'triIndexInLeaf' -- ヒットしたリーフ内の三角形インデックスに応じて 0 から 3

この BVH には重複する AABB が含まれているため、最初のヒットでトラバーサルを停止し、それがこのレイに対して最も近いヒットであると仮定するだけでは不十分です。 このため、新しい '最も近いヒット' が見つかった場合は、'nearestT' がその距離に更新されます。 'nearestT' は、見つけようとしているヒットがあった場合に新しい最大距離として BVH 組み込み関数に渡されます。 確定されたヒットがあるため、その距離を超える距離で発生するヒットは関心の対象ではなくなります。

LOD0 モデルには約 500 万個のポリゴンが含まれており、通常のゲーム コンテンツをはるかに超えてテッセレーションされたモデルを表します。 LOD1-6 は、200,000 個のポリゴンから始まり、各 LOD で半減するため、最新のビデオ ゲームにとってはるかに妥当なレベルのコンテンツを表します。 BVH のサイズは 266 MB から 0.3 MB の間で変動します。

4 つの視覚化モードは次のとおりです:

- 標準 -- このモードでは、単純に、各三角形に一意のインデックスを割り当て、グレースケールの色を生成することにより、各三角形を視覚化します。

- 深度 -- 逆 Z 線形深度値です。

- トラバーサル コスト -- レイの複雑さの 'ヒートマップ' です。 ターゲットにヒット (またはミス) するのに光線が経たステップが多いほど、ピクセルが明るくなります。 表面の近くをかすめる光線は、自由空間を通過する光線やモデルに正面から衝突する光線よりも多くの反復を必要とします。

- プリミティブ -- 'leafIndex' に従った単純な色付けです。 三角形は (三角形ノード内の) 1 個から 4 個の三角形のグループとしてまとめて格納できるので、これらの三角形がどのように格納されたのかを確認するのは興味深い場合があります。

[ボクセル / kescha による Rungholt](https://www.planetminecraft.com/project/rungholt-3505409/)

ボクセル シーンは、オンラインで入手可能な Rungholt データセットからの 1,670 万個のボクセルで構成されています。 ドラゴン データセットと同様に、このモデルは Intel のEmbree BVH ビルダーを使用して構築され、
 は使用できます。 この BVH は、ボクセルがツリーの 'リーフ' 型として扱われる、つまり、BVH に三角形が格納されないということにより、他のシーンとは異なります。 BVH の上位レベルは三角形のシーンと同じ方法で格納されますが、リーフ ノードの '子ポインター' には予約ビットがあり、それらが実際にはリーフであり、それ以上のトラバーサルが必要ないことを示します (ビット 30、0x40000000)。 下位 30 ビットは、先ほどヒットした AABB の位置をエンコードし (`11_8_11` -- XYZ 形式で格納されます)、最大 2048 x 256 x 2048 のサイズのデータセットが可能になります。

この情報を子ノード ポインター自体に格納する利点は、BVH と共に補助的データ構造体を格納する必要がないということです。 この情報は、追加の読み込み操作なしで、BVH 組み込み関数によって直接返されます。

三角形 BVH とは対照的に、この BVH には、1 つの AABB ノード内に重複する AABB が含まれていません。 この保証により、最初のヒットが発生した時点でトラバーサルを終了でき、距離がより短いヒットがLDS スタックに存在するかどうかを考慮する必要がありません。 そのため、トラバーサル ルーチン (RaytraceVoxels.hlsl) は、三角形ルーチンよりもよりシンプルです。

ただし、最初の (かつ最も近い) ヒットが見つかった後、BVH 組み込み関数からは、ヒット距離や、ヒットが発生した AABB 自体の座標に関する情報が提供されません。 得られる唯一の情報は、どのブロックがヒットされたかです。 このため、AABB のどの面にどの距離でヒットしたかを判断するのに役立つ、ALU (AABBIntersect) で実行される追加の手順があります。 これらの 2 つの情報だけで、ボクセルの照射とシェーディングを行えます。 ボクセルにテクスチャを付ける場合は、'レイ エンド' の位置をテクスチャ座標に簡単に変換できます。

その後、サンプルは 1 ピクセルあたり最大 3 つの光線を発射します。 これらの光線は次のものとなります:

1) 直接照明のための簡単な方向影の光線。

2) 水およびガラスの表面から反射光線。

3) 反射面上の直接照度を特定するための影反射光線を。

関数の呼び出しや再帰は必要ありません。これは単なる反復プロセスであり、今後は必要に応じて、それ以上のパスを行うことなく、アンビエント オクルージョン、屈折、またはグローバル イルミネーションに拡張できます。

ブロックごとの 'ID' (1 バイト) をが含まれている別個の補助構造体は、ヒットしたブロックの種類を示します。 子ポインター ストア "ブロック位置" を使用する場合には FP16 AABB ノードで使用可能な予備ビットがないため、これは、BVH 内の位置から導き出されるインデックスに基づいてバッファーから取得する必要があります。
